# 面向校园场景的低成本自助打印系统设计与实现

**摘要**：针对校园自助打印中彩色计价不透明、打印前错误难发现、多设备选择依赖经验的问题，本文设计并实现了一套低成本自助打印系统。系统采用 FastAPI + SQLite 构建服务端，用户端使用 Vue 3，打印端在 Windows 上通过 SumatraPDF 调用现有打印机，无需改造打印机硬件。主要工作包括：（1）设计按页色彩覆盖率分档的计价方法，将彩色页划分为近黑白、低覆盖、中覆盖和全彩四档，并在前端预估与后端结算之间保持一致；（2）实现打印前检查，自动识别空白页、彩色页、贴边页和横竖版混排；（3）设计融合距离、设备能力、纸张余量与队列长度的多机推荐方法；（4）给出系统实现与初步功能验证。在 4 页样张上，覆盖率分档计价将彩色单面价格从 3.20 元降至 2.14 元，彩色双面从 3.00 元降至 2.01 元，前后端计价结果一致。系统已在 1 台 HP Smart Tank 518 上完成部署，【待填：累计订单数】笔订单的运行数据仍在采集。

**关键词**：自助打印；色彩覆盖率；打印前检查；多机协同；低成本部署

---

## 1 引言

校园自助打印的需求集中在三个场景：课程作业、论文/报告、简历与证件材料。现有自助打印系统通常由厂商提供整套软硬件，价格高、封闭性强；小型文印店则依赖人工收银和人工取件，难以做到 7×24 小时无人值守。对于预算有限的校园团队，常见做法是“一台普通打印机 + 一台电脑 + 一个收款码”，但这种方式存在三个问题：

1. **彩色计价不透明**：传统按“黑白/彩色”二元计价，一页只有一个小红章也按整页彩色收费，用户容易觉得不公平；商家也无法区分低覆盖与高覆盖页的墨量成本。
2. **打印前错误难发现**：空白页、贴边、横竖版混排、彩色页误选黑白等问题，往往在出纸后才被发现，造成重复打印和纠纷。
3. **多设备选择靠经验**：当有多台打印机时，用户不知道哪台在线、哪台排队短、哪台纸量足够，容易出现“排错队”或“打到一半没纸”。

本文的目标不是提出新的打印硬件，而是在**不改造打印机、不依赖厂商云**的前提下，用软件把上述问题补齐。系统面向 HP Smart Tank 518 这类消费级喷墨打印机：它没有开放 API，Windows 端只能通过驱动或 SumatraPDF 提交任务。本文的主要工作如下：

- 设计并实现按页色彩覆盖率分档的计价方法，前端预估与后端结算共用同一套规则；
- 实现打印前检查，覆盖空白页、彩色页、贴边页与横竖版混排；
- 设计多机推荐方法，综合距离、设备能力、纸量与队列；
- 完成系统实现与真实打印机上的功能验证，并给出可复现的评估方案。

需要说明的是，空白页删除、彩色转灰度、打印前成本估算、多打印机调度分别已有产品或在先技术（见第 2 节）。本文不主张这些单点的首创性，贡献在于面向低成本校园场景的系统集成、覆盖率计价的前后端一致性，以及可部署的工程实现。

## 2 相关工作

**自助打印与云打印**。现有商用方案通常由打印管理软件、认证终端和计费系统组成，功能完整但部署成本较高；云打印方案依赖厂商云或第三方平台，适合标准化设备，不适合“普通打印机 + 普通电脑”的低成本场景。

**打印成本估算与覆盖率计价**。按墨量或覆盖率估算打印成本在商业印刷中已有应用，例如根据打印作业特征估算墨量[7]。本文将其简化为“逐页彩色像素占比分档”，以便在自助终端中实时展示和结算。

**打印前检查与页面优化**。佳能等厂商的复合机提供“跳过空白页”“保留打印”等功能[1]；Lexmark 打印驱动提供“空白页：打印/不打印”选项[2]；已有专利申请根据文件特征（空白页、低质量图片、彩色显著程度）推荐省耗材打印模式，并展示节省信息[3]。此外，混合彩色/非彩色页的打印控制[4]、双面打印的奇偶页处理[5][6]也已有公开。本文的打印前检查与这些工作方向一致，但实现更轻量，且与覆盖率计价、订单流程绑定。

**多打印机调度**。已有工作按打印类型拆分任务、预测故障并进行负载均衡[8]，或将任务拆分为子任务后由多台打印机协作完成[9]。本文的场景只有少量设备，因此采用可解释的加权评分，而不是复杂的调度模型；距离项在浏览器可定位时启用，否则退化为能力/纸量/队列评分。

## 3 系统设计

### 3.1 总体架构

系统由四部分组成：

- **用户端**：Vue 3 单页应用，负责上传、文件设置、价格预估、下单、订单跟踪与取件提示。
- **管理端**：静态页面，负责设备、订单、告警、价格、账单与接入状态。
- **服务端**：FastAPI + SQLite，负责文件转换、计价、订单队列、设备心跳、告警与支付流水。
- **打印端**：Windows 上的 Python 客户端，轮询订单，下载 PDF，通过 SumatraPDF 静默打印到本机打印机队列，并上报打印中/成功/失败。

数据流为：上传文件 → 转换为 PDF → 打印前检查 → 选择参数并计价 → 支付/下单 → 进入设备队列 → 打印端取单 → 打印并上报 → 用户取件。

### 3.2 按页色彩覆盖率分档计价

**覆盖率定义**。对每一页以 50 dpi 渲染，按固定步长抽样像素。若像素满足
`max(R,G,B) - min(R,G,B) > 30` 且 `max(R,G,B) > 60`，则视为彩色像素。覆盖率
`c = 彩色像素数 / 抽样像素数`。该定义只用于计价与提示，不用于判断打印质量。

**档位与价格**。设黑白单面价为 `p_bw`，彩色单面价为 `p_color`，则单页价格：

- `c < 0.5%`：按黑白价 `p_bw`；
- `0.5% ≤ c ≤ 5%`：`0.5 × p_color`；
- `5% < c ≤ 30%`：`0.8 × p_color`；
- `c > 30%`：`p_color`。

双面打印按“张”计价。设一张纸两面覆盖率分别为 `c1、c2`，先按上式得到两面单页价 `p1、p2`，再乘以双面折扣比例：

`p_sheet = (p1 + p2) × p_color_duplex / (2 × p_color)`

若两面都无彩色（`c1、c2 < 0.5%`），则直接使用黑白双面价 `p_bw_duplex`。奇数页的最后一页按单页价计算。

**前后端一致性**。服务端在 `/api/price` 中返回当前设备的四档单价与覆盖率配置；前端用同一组阈值和系数计算预估；下单时服务端根据实际打印范围重新逐页分析并结算，不信任前端传来的金额。这样即使前端数据未加载完成，最终金额仍以服务端为准。

**复杂度**。单页分析为一次低分辨率渲染加线性抽样，时间复杂度与页数线性相关；结算时最多分析 200 页，超出部分按全彩价，避免超大文件拖慢下单请求。

### 3.3 打印前检查

对转换后的 PDF 逐页检查：

1. **空白页**：页面没有文字、图片或矢量图形时判定为空白；
2. **彩色页**：先检查文字 span 的颜色，再用低分辨率渲染抽样兜底识别彩色图片/色块；
3. **贴边**：计算文字/图片/矢量内容的外接框，若距纸边小于 4 mm 则提示；
4. **横竖版混排**：以出现次数最多的页面方向为基准，标记方向不同的页面。

检查结果只提示、不拦截，用户仍可继续下单。检查默认分析前 100 页；结算时按实际打印范围分析，避免“检查范围”和“计费范围”不一致。

### 3.4 多机协同推荐

推荐输入包括本次订单的页数、预计用纸张数、是否需要彩色、是否需要双面、纸张规格，以及可选的用户经纬度。对每台在线设备计算：

- **预计等待**：`wait = (该机排队页数 + 本次页数) / 该机速度`；
- **距离项**：若用户与设备都有经纬度，按 Haversine 直线距离折算，1 km 约等于 5 分钟；
- **能力惩罚**：不支持彩色 +100，不支持自动双面 +20；
- **纸量惩罚**：预计用纸超过剩余张数 +30。

总分越低越优。服务端返回推荐设备、候选列表、每台的推荐理由与惩罚项；用户端显示“推荐”徽标与理由，用户可手动改选，手动选择后不再被自动覆盖。没有定位授权时，距离项不参与评分，界面如实提示“距离未启用”。

### 3.5 订单状态与交付

订单状态为 `pending → printing → completed / failed`。打印端在取单后先上报 `printing`，真正打印完成再上报 `success`，失败上报 `failed`；服务端对重复上报做幂等处理，避免重复累计用纸。设备心跳超过 60 秒未更新即视为离线；告警引擎对纸量不足、离线、UPS 市电中断、门磁异常、取件顺序异常进行规则判定。本文不展开告警规则，重点在计价、检查与调度。

## 4 实现

系统实现的技术栈与关键点如下：

| 模块 | 技术 | 说明 |
|---|---|---|
| 服务端 | FastAPI + SQLite（WAL） | 统一 `ReturnResult{code,message,data}`；用户端 JWT，管理端/打印端密钥 |
| 用户端 | Vue 3 + Element Plus | 上传、参数设置、覆盖率提示、价格预估、订单跟踪 |
| 管理端 | 原生 HTML/CSS/JS | 设备、订单、告警、价格、账单、接入状态 |
| 文件转换 | WPS/LibreOffice headless | 统一转为 PDF；图片转 PDF |
| 页面分析 | PyMuPDF | 渲染抽样、文字颜色、外接框、缩略图 |
| 打印端 | Python + SumatraPDF | Windows 下静默打印；Linux 下 ipptool/CUPS |
| 部署 | 云服务器 + systemd | 单实例部署；静态资源由 FastAPI 托管 |

实现中的两个关键点：

1. **文件名映射**：上传的是原始文件，转换后统一为 PDF；入队、下载、打印、订单查询都使用转换后的文件名，避免图片/文档在打印端找不到文件。
2. **计价一致性**：覆盖率阈值与折扣系数由服务端下发；前端只做预估，服务端在 `/pay/bill/create` 中重新分析实际页范围并结算。前端与后端使用相同的双面配对规则，避免“单面/双面/奇数页”边界不一致。

## 5 评估

### 5.1 实验设置

- 打印机：HP Smart Tank 518（喷墨、A4、手动双面、100 张纸盒）；
- 打印端：Windows 10/11，Python 3，SumatraPDF；
- 服务端：云服务器，FastAPI + SQLite；
- 样张：4 页 PDF，红块面积分别约为 0%、2.5%、16%、37%，用于覆盖四个档位；
- 评估环境：本地与线上各执行一次，记录金额、覆盖率与页面检查结果。

### 5.2 功能验证

4 页样张的覆盖率与档位如下：

| 页码 | 彩色覆盖率 | 档位 | 单页价格（彩色单面） |
|---|---|---|---|
| 1 | 0% | 近黑白 | 0.30 元 |
| 2 | 2.9% | 低覆盖 | 0.40 元 |
| 3 | 16.4% | 中覆盖 | 0.64 元 |
| 4 | 37.0% | 全彩 | 0.80 元 |

计价结果：

| 场景 | 覆盖率分档 | 原全彩价 | 结果 |
|---|---|---|---|
| 彩色单面 4 页 | 2.14 元 | 3.20 元 | 节省 1.06 元 |
| 彩色双面 4 页 | 2.01 元 | 3.00 元 | 节省 0.99 元 |
| 黑白单面 4 页 | 1.20 元 | 1.20 元 | 不变 |

本地与线上结果一致；同一订单的前端预估与后端结算金额一致。该验证只说明计价规则在样张上可复现，不代表大规模用户节省。

### 5.3 评估方案（数据待补）

为形成完整论文，建议补充以下实验，结果用真实数据填写，不得编造：

1. **覆盖率估计误差**：随机抽取 50 页，人工标注彩色区域面积作为真值，计算平均绝对误差与档位分类准确率；记录单页分析耗时。
2. **计价一致性**：随机生成 100 组“页数 × 份数 × 单双面 × 色彩 × 覆盖率”组合，比较前端预估与后端结算，统计不一致率。
3. **打印前检查**：构造 100 页测试集（空白页、彩色页、贴边页、横竖版混排各若干），统计精确率、召回率与误报。
4. **多机推荐**：在 2–3 台设备上模拟不同队列/纸量/能力，比较“随机选择”“手动选择”“推荐选择”的平均等待时间与失败率。
5. **部署数据**：统计上线前后的订单数、平均金额、重复打印率、用户问卷满意度（5 级量表），并匿名化处理。

## 6 讨论与局限

**覆盖率计价的公平性与边界**。按覆盖率分档可以降低低覆盖彩色页的价格，但系统仍然按彩色出纸；折扣是计价策略，不是实际灰度打印。若要在物理上省墨，需要生成灰度修正文件或按页切换色彩模式，这会带来画质与实现复杂度的权衡。

**打印前检查的能力边界**。当前检查只覆盖版面级问题（空白、彩色、贴边、方向），不判断“文件传错”“内容写错”等语义问题；细小彩色文字可能被归入“近黑白”档。

**多机推荐的冷启动**。设备能力（彩色/双面/速度）需要人工配置；未配置时按“不排除”处理。距离依赖浏览器定位与 HTTPS，当前 HTTP 部署下不可用，推荐退化为能力/纸量/队列评分。

**部署规模**。目前只在一台设备上验证，样本量有限；没有对照组，用户节省与满意度数据仍需积累。覆盖率估计采用像素抽样，和真实墨量之间存在误差；纸张余量为估算值，不是称重。

**与在先技术的关系**。空白页删除、彩色转灰度、打印前成本估算、多打印机调度均有公开资料[1]–[9]。本文的定位是低成本系统集成与覆盖率计价的工程实现，不主张单点首创。

## 7 结论

本文面向校园低成本自助打印场景，设计并实现了一套由用户端、管理端、服务端和 Windows 打印端组成的系统。系统在不改造打印机的前提下，实现了按页色彩覆盖率分档计价、打印前检查、多机推荐和订单状态跟踪。4 页样张验证表明，覆盖率计价可以把彩色单面价格从 3.20 元降到 2.14 元、彩色双面从 3.00 元降到 2.01 元，且前后端结果一致。后续工作包括：生成灰度修正文件以实现真实省墨、接入 IPP/打印日志做打印完成验证、增加出纸口传感器，以及在多站点积累部署数据。
